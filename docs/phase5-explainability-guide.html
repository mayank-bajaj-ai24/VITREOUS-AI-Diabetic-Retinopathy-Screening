NETRA Phase 5 — Explainability

A line-by-line guide to the code: what it does, how it works, why each technology and each number was chosen. Written to be re-read, and updated as the project changes.

Branch: Kathan MATLAB R2026a Owner: Kathan Last updated: 2026-09-14
Scope of this module. Four production files plus a dev stub, a demo and tests: generate_gradcam.m, temperature_scaling.m (+ apply_temperature.m), attention_lesion_iou.m, and generate_pdf_report.m. Together they make the DR grading model explain itself: show where it looked, prove it looked at real disease, and make its confidence number honest — then print all of it on one clinical page.
Status: validated ✓ — run on MATLAB Online (R2026a, Update 5) with Deep Learning, Image Processing and Statistics toolboxes. All 14 unit tests pass, and run_explainability_demo runs the full chain on a real fundus image and writes a PDF report (temperature scaling fitted T = 2.93, ECE 0.202 → 0.071). The grade and heatmap remain meaningless until Phase 4's grading model exists — the code runs against a random-weight stub. See Honest caveats.

The 4 design decisions that shaped everything

If you understand these four, the code reads itself. Every file is an expression of them.

Decision 1 — Cross the Phase 4 boundary with plain arrays, never Phase 4's objects

temperature_scaling takes a logits matrix and a labels vector — not "the Phase 4 model". attention_lesion_iou takes a score map and Phase 3's result — not "the grading pipeline".

Why. Phase 4 doesn't exist yet, and we can't know exactly how your teammate will structure it. If my code reached into Phase 4's internals, every wrong guess would break it. Passing plain arrays across the boundary means the worst case is a one-line change in the demo glue — never a rewrite. This is decoupling, and it is the single most important idea in the module.

Decision 2 — Develop against a stub, not against nothing

Grad-CAM needs a real network to run. Rather than wait for Phase 4, I built a tiny fake network (make_stub_grading_net) with the right shape but random weights.

Why. It lets every line execute and be tested today. Predictions are meaningless, but the plumbing is real — exactly the "get it running end-to-end, then improve" pattern Phases 3 and 4 recommend.

Decision 3 — Compute everything on the 512×512 canvas

Grad-CAM attention and Phase 3 lesion masks must be compared pixel-to-pixel, so both must live on the same coordinate frame: the enhanced 512 canvas.

Why. The plan is explicit — both already share that canvas, so no mask resampling is needed, and I must not map back to the clinician's original image for the metric (that round-trip through invert_geometry is lossy because Phase 2 downsamples). Map back only for display.

Decision 4 — Prefer base MATLAB over add-ons

The PDF report uses exportgraphics (built in) instead of the Report Generator toolbox; calibration uses fminbnd (built in) instead of the Optimization Toolbox.

Why. Phases 3 and 4 both lost time to missing add-ons (ONNX converter, pretrained weights). Base-MATLAB code always runs, which for a demo is worth more than polish.

1 · apply_temperature.m

matlab/explainability/apply_temperature.m the foundation · reused everywhere

The concept

A classifier outputs logits (raw scores, any real number). Softmax turns them into probabilities. Temperature scaling inserts one number T: instead of softmax(logits), compute softmax(logits / T).

  • T = 1 → nothing changes.
  • T > 1 → logits shrink toward 0 → probabilities move toward uniform → less confident.
  • T < 1 → logits spread apart → more confident.
Why it can't change the diagnosis. Dividing every logit by the same positive number never changes which one is largest. So the predicted grade never moves — only the confidence attached to it. That is what makes temperature scaling safe: it cannot turn a "grade 2" into a "grade 3".

Line by line

if ~isscalar(T) || ~isfinite(T) || T <= 0
    error('NETRA:InvalidTemperature', ...

T must be one positive, finite number. T ≤ 0 is nonsensical (negative flips the ranking; zero divides by zero). I fail loudly with a NETRA: error code, matching the repo convention so callers can try/catch on it.

if isvector(logits)
    logits = logits(:).';
end

If someone passes a single image's 5 logits as a column, reshape to one row. Makes the function work for both "one sample" and "a whole batch".

z = z - max(z, [], 2);   % stability
e = exp(z);
probs = e ./ sum(e, 2);

This is the numerically stable softmax — the one non-obvious part. Softmax is unchanged if you subtract any constant from every element (it cancels top and bottom). But computationally exp(1000) overflows to Inf → NaN. Subtracting the per-row max makes the largest exponent exp(0)=1, so nothing overflows and the result is identical. [],2 means "operate along dimension 2" — across classes, within each row.

Why a separate file? Two places apply temperature — temperature_scaling when fitting T, and inference code when using the fitted T later. If they drifted apart you'd get subtle calibration bugs. One file, one source of truth.

2 · temperature_scaling.m

matlab/explainability/temperature_scaling.m fits T from held-out logits + labels
Why temperature scaling and not something fancier? Modern networks are systematically overconfident — the finding of Guo et al., "On Calibration of Modern Neural Networks" (2017). For a screening tool the confidence number is clinical information: it decides whether a borderline grade is trusted or sent to a human. Temperature scaling is the standard fix because it is the minimal correction (one parameter — can't overfit a small validation set), it provably preserves accuracy, and Guo et al. showed it beats more complex methods on exactly this problem.

The three-level settings pattern (used in every file)

bounds = local_setting(options, 'Bounds', cfg, {'calibration','temperature_bounds'}, [0.05, 10.0]);

Reads a setting with a fallback chain: explicit options.Bounds wins → else the config value at cfg.calibration.temperature_bounds → else a hardcoded default. So a caller can override per-call, the team can set project defaults in the YAML, and the function still works with an empty config.

Label normalization — the 0-vs-1 trap

labels = local_normalise_labels(labels, C, N);   % -> N×1 in 1..C

ICDR grades are 0–4 (medical convention). MATLAB indexing is 1–5. Guess wrong and every label is off by one → calibration is garbage. So the helper detects the convention: values fitting 1..C are left; values fitting 0..C-1 get +1; anything else errors. Your teammate can hand me labels in either convention. The test testTemperatureLabelEncodingAgnostic proves both give the identical T.

The objective — negative log-likelihood

true_idx = sub2ind([N, C], (1:N).', labels);
nll = @(T) local_nll(logits, true_idx, T);

sub2ind turns "(row i, true-class column)" into linear indices, so probs(true_idx) plucks the probability of the correct answer for every sample at once — no loop. The objective is NLL = -mean(log(prob of true class)).

Why NLL, not "minimize ECE directly"? NLL is smooth and differentiable in T; ECE is piecewise-constant (it jumps as samples cross bin boundaries) and is a terrible thing to optimize. Guo et al. fit on NLL and report ECE — exactly what this does.

The optimizer

[T, nll_after] = fminbnd(nll, bounds(1), bounds(2));
Why fminbnd? T is a single scalar and NLL(T) is smooth and unimodal (one valley). A bounded 1-D search is exactly the right tool — no gradients, no toolbox add-on, no learning rate, and it can't run to infinity. The simple tool is also the correct tool.

Why bounds [0.05, 10]? T must be positive. An overconfident model needs T>1, typically 1–3 in practice. 10 is a generous ceiling — wanting more signals a wrong split. 0.05 guards the underconfident direction. Wide enough never to clip a real answer, bounded enough to stay well-posed.

Expected Calibration Error

[conf, pred] = max(probs, [], 2);
correct = (pred == labels);
edges = linspace(0, 1, num_bins + 1);
...
edges(end) = edges(end) + eps;

ECE measures the gap between confidence and reality. Group predictions into bins by their confidence (top probability). In the "80–87% confident" bin, if the model is actually right 80–87% of the time it's well-calibrated there. ECE = average |accuracy − confidence| across bins, weighted by bin size. Zero = perfect. The + eps nudge on the last edge includes a confidence of exactly 1.0, which the half-open bins [lo,hi) would otherwise drop.

Why num_bins = 15? The value from Guo et al. 2017 — the field standard: enough bins to resolve the curve, few enough that each has samples.

Returns: T, NLL & ECE before/after, accuracy (unchanged — a sanity anchor; if scaling moved it, there's a bug), and full per-bin reliability data so you can plot a reliability diagram.

3 · generate_gradcam.m

matlab/explainability/generate_gradcam.m touches the R2026a gradCAM API

The concept

Grad-CAM (Selvaraju et al., 2017) answers "which pixels drove this prediction?". It takes the score for one class, computes how sensitive that score is to each feature map in a late convolution layer (the gradient), uses those sensitivities as weights, and produces a coarse heatmap. On a retina, a trustworthy grader's heat sits on lesions; heat on the border or optic disc is a red flag you can now show.

Why a late conv layer specifically? Early conv layers see edges/textures (no class meaning); the final classifier has lost all spatial layout (a flat vector). The last convolution layer is the sweet spot — it still has a spatial grid and carries class meaning. That's also why the result is coarse (that grid is small, e.g. 16×16, then upsampled).

Preparing the canvas

canvas = local_prepare_canvas(image_input, cfg, options.Enhanced);   % 512×512×3

Reproduces the exact Phase 1 + Phase 2 pipeline (quality_gate then enhance_fundus) that the rest of NETRA uses — copied from segment_lesions.m so the canvas is bit-identical. The whole point is that the heatmap aligns with Phase 3 masks, and they only align on the identical enhanced 512 canvas. If options.Enhanced is true, the caller already has the canvas; we skip re-enhancing and error on a size mismatch (a silent misalignment otherwise).

Resize to the network's own input size

net_in = local_net_input_size(net);   % reads the input layer's InputSize
X = imresize(canvas, net_in(1:2));
Why read the size off the network? ResNet-50 wants 224×224, EfficientNet-B4 wants 380×380 (a Phase 4 pitfall the plan flags). Instead of hardcoding, I read InputSize from the net's input layer, so the same code works for whichever backbone Phase 4 ships. Run at native size, then upsample the heatmap back to 512 for mask comparison.

The prediction (dlnetwork mechanics)

dlX = dlarray(single(X), 'SSCB');
y = predict(net, dlX);
scores = double(gather(extractdata(y))).';

A dlnetwork wants a dlarray tagged with a format: 'SSCB' = Spatial, Spatial, Channel, Batch — "this is an image, H×W×C×batch". extractdata pulls the raw numbers out of the returned dlarray; gather brings them off the GPU if there is one; single because networks run in single precision.

The feature layer — deliberately loud

if isempty(char(feat_layer))
    feat_layer = local_last_conv_layer(net);
    auto_layer = true;
    warning('NETRA:GradCAMAutoLayer', ...);
end
Why warn instead of silently picking? For a two-branch model (ResNet ∥ EfficientNet) the layer choice is a real editorial decision, and the report must state which branch it explains. If you set the layer (config or g.gradcam_layer), I use it. If not, I auto-detect the last conv layer and warn that a final figure should choose deliberately.

The Grad-CAM call — three R2026a specifics

score_map = gradCAM(net, X, class_idx, ...
    'FeatureLayer', feat_layer, 'ReductionLayer', red_layer);
  • It's gradCAM — capital CAM. The plan's prose says gradcam in places, which does not exist on R2026a. A documented API correction.
  • I pass the class index and an explicit ReductionLayer ('softmax'). For a generic dlnetwork, gradCAM must be told which output to reduce over and which conv layer to read; being explicit stops it guessing wrong.
  • It's wrapped in try/catch → NETRA:GradCAMFailed naming both layers and pointing at analyzeNetwork. When a layer name is wrong you get an actionable message, not a cryptic trace.

Normalize and overlay

score_map = local_normalise01(double(score_map));

local_normalise01 rescales to [0,1] and handles the flat-map case: a uniform map (max == min) would divide by zero → NaN; instead it returns all-zeros. A uniform map is exactly the symptom of a wrong layer choice, so this keeps the failure visible instead of poisoning downstream math.

blended = (1 - alpha) * base + alpha * heat_rgb;   % alpha = 0.45

Why alpha = 0.45? Below ~0.3 the heat is too faint over a red-orange fundus; above ~0.6 it hides the retina. 0.45 keeps both anatomy and attention visible. A legibility choice, config-exposed.

Returns the map at two resolutions — native and upsampled-to-512 — because the IoU function and the overlay both need the 512 version, while the native map is the honest true resolution.

4 · attention_lesion_iou.m

matlab/explainability/attention_lesion_iou.m the key result of Phase 5

The plan calls this "the most valuable single result in Phase 5" — it is the actual argument that the AI is trustworthy: it looks at real disease, not artifacts.

Restricting to the retina

att(~valid_mask) = 0;
lesion_mask = label_map > 1 & valid_mask;

Phase 3's label map uses 0 = outside the retina, 1 = background inside, 2–5 = the four lesion classes. So label_map > 1 is "any lesion" and valid_mask = label_map > 0 is "inside the retina". Zeroing attention in the black surround stops it inflating every denominator. Tested by testAttentionIgnoresOutsideRetina.

Three measures — and why three, not one

The intellectual core. Grad-CAM is coarse (a ~16×16 grid upsampled); lesions are tiny (a microaneurysm ≈ 4 pixels). A coarse blob can never tightly tile a 4-pixel dot, so raw IoU looks low no matter how good the grader is — a property of the method, not a failure. Reporting only IoU would be dishonestly pessimistic. Hence three complementary numbers.

1 — IoU (the classic, included but understood to be pessimistic)

threshold = prctile(att_valid, pctl);   % pctl = 90
hot = att >= threshold & valid_mask;
iou = intersection(hot, lesions) / union(hot, lesions);

"Hot" = the top 10% most-attended retina pixels. Why the 90th percentile? It defines "where the model is really looking" as the top decile. Too low (50th) → "hot" covers half the retina and means nothing; too high (99th) → a few noisy pixels. 90 is the value the plan's snippet uses. Config-exposed.

2 — attention mass on lesions (the fairer number)

attention_mass_on_lesion = sum(att(lesion_mask)) / sum(att(valid_mask));

"Of all the attention spent anywhere on the retina, what fraction landed on lesion pixels?" This doesn't punish the resolution mismatch — it asks the honest question, and it's usually the headline number. The plan explicitly recommends reporting it alongside IoU.

3 — the control (the "compared to what?" guard)

control = rot90(lesion_mask, 2);   % 180°: same shape, wrong place
control_iou = local_iou(hot, control & valid_mask);
lift = iou - control_iou;
Why a control? A number is meaningless without a baseline. Is IoU 0.15 good? Only if it beats IoU against wrong lesions. Rotating the mask 180° gives the same shape and area in the wrong place. If true-mask IoU beats the control, alignment is real; if equal, the attention isn't aligned with anything. lift > 0 is the one-number verdict. (You can also pass another image's mask via options.ControlMask; rotation is a self-contained proxy needing no second image.)

Per-class breakdown

for k = 1:n_les
    cmask = (label_map == classes.lesion_ids(k)) & valid_mask;
    mass_frac(k) = sum(att(cmask)) / total_mass;
    class_iou(k) = local_iou(hot, cmask);
end

Tells you which lesion type the model attends to — maybe it locks onto bright hard exudates and ignores tiny microaneurysms. Clinically meaningful, and the per-class detail the plan insists on ("read per-class metrics, not averages"). Class names/ids come from lesion_classes(), never hardcoded, so a scheme change follows automatically.

The network architecture

imageInputLayer([512 512 3], 'Normalization','none', 'Name','input')
conv(3,8) → relu → maxpool(2)
conv(3,16) → relu → maxpool(2)
conv(3,32, 'Name','features')   % Grad-CAM target
relu → globalAveragePooling → fullyConnected(5, 'Name','logits') → softmax('Name','softmax')

Why exactly this shape? The minimum that exercises every Phase 5 path honestly:

  • a named late conv layer "features" → Grad-CAM has a real target;
  • a named "logits" layer (pre-softmax) → temperature scaling has real logits to pull;
  • a "softmax" → the reduction layer exists;
  • two maxpools make the features map 128×128 (512→256→128) — genuinely coarser than input, so Grad-CAM's upsampling path is actually tested;
  • filter counts 8/16/32 are tiny — it exists to run fast, not to classify.

rng(seed) makes the random weights reproducible (a test passing today passes tomorrow). Random weights → predictions are noise, which is honest: the stub proves the code runs, never that grading works.

The stub grader returns the interface contract exactly

Fields grade, grade_name, probs, logits, confidence, referable, canvas, gradcam_layer. The most important is logits (pre-softmax) — if Phase 4 returned only softmax probabilities, calibration would be impossible. Modeling it now forces the interface doc to demand it, so Phase 4 is built correctly the first time.

grade = idx - 1;   % 1-based argmax → 0-based ICDR

The same 0-vs-1 boundary as the calibration code — it appears everywhere ICDR meets MATLAB.

6 · generate_pdf_report.m

matlab/reporting/generate_pdf_report.m the visible clinical deliverable
Why exportgraphics, not Report Generator? Report Generator (mlreportgen.*) is a separate add-on not installed on a clean MATLAB — the exact blocker that cost Phases 3 and 4. exportgraphics is base MATLAB and writes a vector PDF from any figure. Less fancy, but it always works.

Layout (redesigned after the first run): manual normalized-coordinate positioning rather than a tile grid, for full control of a clinical look — a teal header band, a severity-coloured grade badge (green→red for ICDR 0→4), a coloured referable strip, three image panels (fundus, lesion overlay, Grad-CAM), a per-grade coloured probability chart with % labels, then two findings cards (a lesion-burden table and an assessment column) and a footer disclaimer.

Why the redesign? The first PDF rendered washed-out: on a themed host (MATLAB Online's dark UI) the figure inherited faint gray text and a black-backed chart while the page was white. The rebuild forces a light theme (fig.Theme = 'light') and sets every colour explicitly, so the report looks identical regardless of the host theme.

Grad-CAM masked to the retina

amap = alpha * double(valid);              % per-pixel alpha, 0 outside retina
blended = base .* (1 - amap) + heat_rgb .* amap;

The raw Grad-CAM overlay painted a bright false rim where stub attention leaked onto the black surround. The report now builds its own overlay with a per-pixel alpha that is zero outside the retina (valid = label_map > 0), so the surround shows the plain fundus and only real retina carries heat — the same "reason only inside the retina" principle as the IoU metric.

Lesion overlay

chan(mask) = 0.5 * chan(mask) + 0.5 * color(ch);

Blend each class's canonical color (from lesion_classes()) 50/50 over the fundus. 50% so you see both the lesion color and the retina underneath (opaque would hide whether the mask is really on a lesion). Then overlay_legend — Phase 3's own renderer, reused so colors match every NETRA figure.

Defensive stat reader

st.pixels = local_field(s, {'pixels','pixel_count','area'}, 0);
Confirm against real r.stats when you run it. I saw the stats described in prose ("pixels, connected regions, area fraction") but not the literal struct field spellings, so local_field tries several plausible names and falls back to 0 (or counts the label map directly). It degrades gracefully instead of crashing — but this is a spot to verify.

Fovea distance in disc diameters

d_px = min(sqrt((xx - fx).^2 + (yy - fy).^2));
dd = d_px / (2 * od.disc_radius);

Clinicians express lesion location as distance from the fovea in disc diameters (DD) — because the same lesion is far more dangerous near the macula. The disc diameter (2 × disc_radius) is the natural ruler. I find the nearest lesion pixel to the fovea (both from Phase 3's r.optic_disc) and divide.

Why the < 1.0 DD "sight-threatening" flag? The macula sits roughly within one disc diameter of the fovea; a lesion inside that radius implies macular involvement — the sight-threatening case. Clinically motivated, stated as such, not tuned. All guarded: a missing fovea (NaN) simply omits the line.

The disclaimer ("Research prototype. Not a medical device.") is pulled from config and always printed — asserting a clinical grade without it is a real problem, so it's structural, not decoration.

7 · run_explainability_demo.m & test_explainability.m

matlab/demo/run_explainability_demo.m · matlab/tests/test_explainability.m

The demo runs the whole chain on one image: real Phase 3 segmentation → stub grade → Grad-CAM → IoU → calibration → PDF, printing a [n/6] line per step, and ending honestly: "grade and Grad-CAM come from an untrained stub model."

The synthetic overconfident set

logits(i, labels(i)) += 2.5;        % true class usually wins
if rand < 0.30                      % but 30% of the time...
    logits(i, wrong) += 3.0;        % a wrong class wins bigger
end
logits = logits * 4.0;              % inflate → overconfidence

No real held-out set exists yet, so I manufacture a classifier that is ~70% accurate but very confident (the ×4.0 makes softmax report near-certainty even when wrong) — precisely the regime temperature scaling fixes. Running it demonstrates T>1 and a drop in ECE. The numbers only produce that qualitative behavior; they're labeled "SYNTHETIC — demo only" and never go in a report.

Tests split by dependency

  • Hermetic tests (temperature, apply_temperature, attention-IoU, report) build synthetic fixtures and need no model or GPU — they run anywhere. local_aligned_fixture builds a circular retina with a square "haemorrhage" and a Gaussian of attention on it, a case where I know the answer.
  • Network tests (stub contract, Grad-CAM shape) need the Deep Learning Toolbox, so they're guarded with assumeTrue(has_dlt, ...) — they skip, not fail, where it's absent.

Tests check properties, not exact values: rows sum to 1, argmax preserved under scaling, T>1 for an overconfident set, IoU ∈ [0,1], the PDF exists and is non-empty. Property tests are right here because exact numbers depend on random weights.

The Phase 4 interface (as delivered)

Phase 4 shipped. The delivered grade_dr_severity differs from the contract Phase 5 was drafted against; full detail in docs/phase5-interface.md. What it actually returns, and how Phase 5 adapts:

Drafted contractRealityPhase 5 adaptation
g.probsg.probabilitiesreport accepts either (local_grade_probs)
g.logits returnednot returned; net ends in softmaxrecover as log(probabilities) — equal to logits up to a constant softmax cancels (collect_grading_logits)
g.canvas returnednot returnedreport pulls it from xai.gradcam.canvas or options.Canvas
g.gradcam_layernot returnedauto-detect recurses into nested backbones + warns, or set explainability.feature_layer
— adds options.Temperaturethe inference hook our calibration feeds its fitted T into
The log-probability trick. Their network ends in softmax, so it never exposes raw logits. But for a softmax, log(p_i) = z_i − logsumexp(z) — the log-probabilities equal the true logits z up to a per-sample constant. That constant cancels inside softmax, so temperature scaling fitted on log(p) recovers exactly the same T and the same calibrated probabilities as fitting on z. So no change to Phase 4 is needed — collect_grading_logits just takes log(probabilities) over the held-out split.

Grad-CAM on the nested hybrid — resolved with an occlusion fallback

The grading model wraps each backbone in a networkLayer (resnet, effnet), so its conv layers are nested, not on the top-level graph. Running it confirmed the fear: gradCAM cannot address a convolution nested inside a networkLayer — it fails with "Layer … does not exist", regardless of how the name is spelled.

The fix — fall back to occlusion sensitivity. Instead of fighting the layer addressing, generate_gradcam now tries Grad-CAM first and, on failure, computes an occlusion-sensitivity map: it slides an occluding patch across the image and measures how much each position's removal drops the predicted class score — the regions that hurt the score most are the ones the model relies on. Crucially it calls the network only through predict, so a nested architecture is no obstacle. It is a standard, citable XAI method, deliberately coarse (large patch/stride) to stay fast on CPU and to match Grad-CAM's own resolution. The attention-IoU, the overlay and the report all consume the resulting map unchanged; the report simply labels the panel "Occlusion sensitivity" instead of "Grad-CAM". A flat network (like the dev stub) still uses true Grad-CAM.

Honest caveats (so you can defend the work)

  1. Validated on MATLAB Online R2026a (2026-09-14). All 14 unit tests pass and the end-to-end demo runs and writes a PDF. The two interface points I flagged as risky both held up in practice: the gradCAM call (verified by testGradCAMShapeAndRange) and the report's defensive r.stats reader (the demo rendered a report without error). They still fail loudly with NETRA: messages if a future change breaks them.
  2. Grade and heatmap are meaningless until Phase 4 exists — random-weight stub. Code paths are real and tested; predictions are not.
  3. The design is deliberately conservative at the Phase 4 boundary — plain arrays across the interface — so a wrong guess about Phase 4's internals costs a one-line demo change, never a rewrite.
